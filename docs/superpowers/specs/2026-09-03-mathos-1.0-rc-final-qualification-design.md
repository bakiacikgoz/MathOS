# MathOS 1.0 RC Final Qualification Design

## Purpose

Qualify the existing MathOS 1.0 release candidate through real product paths on Windows 11 x64 and macOS arm64, fix only defects exposed by qualification, and publish `v1.0.0-rc.1` only when every mandatory gate has current, platform-specific evidence.

The binding requirement source is the user-supplied “MATHOS 1.0 RC — LIVE MODEL, SANDBOX, CROSS-PLATFORM & FINAL RELEASE CLOSURE” plan. This design defines how that plan will be executed in this repository without weakening its trust rules.

## Repository and Change Policy

- Work only on `main`.
- Do not create branches or worktrees.
- Preserve canonical history containing `71ec76c2e27553a816693d64bdc16750edcc1e3a`.
- Make small, atomic commits for verified defect fixes and qualification infrastructure changes, then push directly to `origin/main`.
- Never use force push, force tags, destructive resets, or blind cleanup.
- Generate all release evidence from the current final `main` HEAD. Historical artifacts are not qualification evidence.
- Keep CodeGraph index data local and ignored; use CodeGraph before textual code discovery.

## Execution Strategy

Qualification proceeds from evidence to defects, not from speculative implementation. Existing provider, verification, sandbox, TUI, Atlas, extension, packaging, reproducibility, and publication subsystems remain authoritative. Each real qualification path is exercised first; only a reproducible failure attributable to MathOS authorizes a code change.

Defect changes follow a test-driven cycle:

1. Capture the failing real path and reduce it to the smallest meaningful regression test where feasible.
2. Confirm the regression test fails for the observed reason.
3. Implement the smallest production correction without weakening policy or epistemic boundaries.
4. Run focused tests, affected tests, and the relevant real qualification path.
5. Commit and push the independently verified slice on `main`.

## Evidence Model

Every result must be classified as one of:

- `CODE_TESTED`: deterministic automated coverage without a live external capability.
- `LIVE_TESTED`: a real provider, runtime, or application interaction was exercised.
- `PLATFORM_TESTED`: evidence was produced on the named real target platform.
- `USER_ACTION_REQUIRED`: an official login, OS confirmation, or human semantic review is pending.
- `NOT_CONFIGURED`: optional credentials or services were not supplied.
- `NOT_AVAILABLE`: required hardware, host, runtime, or application is absent.
- `POLICY_BLOCKED`: the existing provider policy correctly denied the path.

Mock providers, fixtures, cross-compilation, package inspection, and installation detection cannot satisfy live or platform gates. Evidence records must include final Git revision, platform, command or interaction identity, timestamps, sanitized runtime metadata, result, and artifact hashes where applicable. They must not include credentials, tokens, cookies, authorization headers, or secret-store values.

## Windows Qualification

The current Windows 11 x64 machine is the authoritative Windows host. Qualification must exercise release artifacts rather than relying solely on the source checkout.

The Windows sequence is:

1. Verify host, toolchain, Codex, VS Code, OCI sandbox runtime, Lean/Lake, and packaging prerequisites.
2. Use the official Codex-managed subscription session. If authentication is absent, invoke only the official browser or device login flow and pause for the user.
3. Run a real structured-output completion through the MathOS Provider Hub and prove that no PAYG fallback occurred.
4. Persistently assign the selected Codex profile to planner, researcher, formalizer, and prover roles; reopen MathOS and verify runtime resolution.
5. Exercise a real Research Planner invocation and confirm model output cannot mutate verification or fidelity authority.
6. Run the real production sandbox attack matrix through the MathOS computation path, including network, environment, filesystem, timeout, output, child-process, temporary-home, and fail-closed checks.
7. Build and extract the Windows x64 standalone artifact, then exercise version, doctor, CLI, real terminal TUI, workspace, Atlas, and source-tree independence.
8. Install the VSIX into a real VS Code Extension Host and verify activation, trees, commands, provider persistence, bridge health, and clean teardown.
9. Execute the C-001 live research, formalization, human fidelity, Lean verification, persistence, Atlas, reproducibility, and publication chain.
10. Produce revision-bound Windows evidence and checksums.

Ordinary subprocess execution with filtered environment variables is not an acceptable Windows sandbox. If the supported production isolation backend cannot provide the required guarantees, the sandbox gate remains blocked.

## C-001 Trust Chain

The canonical claim is “For every natural n, the sum of the first n odd natural numbers equals n squared.” The existing real formalization and proof path must be reused unless current revision rules require regeneration.

The model may produce research actions, formalization reasoning, and proof strategy suggestions through typed persistent MathOS paths. Model output remains unverified evidence and cannot assign `HUMAN_APPROVED`, `KERNEL_VERIFIED`, claim status, or verification status.

Before fidelity approval, execution pauses and presents:

- the exact natural-language claim;
- the exact current Lean theorem statement;
- explicit assumptions and domain;
- a faithful natural-language back-translation.

Only an explicit user approval is recorded through the official MathOS fidelity mechanism with human/local-user audit identity and current claim/formal revisions. The agent never supplies that decision.

After approval, the real pinned Lean/Lake/Mathlib pipeline must compile the theorem, inspect axioms and forbidden constructs, validate current revisions and toolchain pins, and pass the existing VerificationGate. `KERNEL_VERIFIED` may only result from that gate. Direct database status mutation and authority bypasses are prohibited.

MathOS is then closed and reopened to verify persistence of the objective, claim, formalization, fidelity decision, proof metadata, kernel evidence, verification state, and provider role configuration without workspace credential persistence.

## Reproducibility and Publication

The verified C-001 state must produce a capsule containing version, final Git revision, claim and formal revisions, Lean and Mathlib/toolchain identity, proof hash, provider/profile and model identifiers, sanitized transport metadata, research evidence hashes, and verification result. Capsule verification must pass and a secret scan must be clean.

Publication/export must expose the verified theorem, formal statement, proof metadata, and capsule reference while keeping model reasoning clearly distinct from verified proof evidence.

## macOS Qualification

macOS arm64 qualification uses the same final HEAD and the same acceptance matrix on an accessible real Apple Silicon host. Windows evidence cannot be reused as macOS evidence, and cross-built artifacts cannot establish runtime behavior.

If no authorized real macOS arm64 host is accessible, portable artifacts, commands, expected checks, and the evidence schema will be prepared, but macOS remains `NOT_VERIFIED`; release remains blocked and no tag or GitHub release is created.

## Regression, Security, and Billing Closure

After real defects are fixed, run the frozen install, typecheck, build, full test suite, provider contract and qualification suites, sandbox security checks, VSIX verification, standalone verification, software-completion checks, final-product capabilities, and release-check.

Perform final scans across the working tree, task-created Git history, reports, logs, databases, capsules, VSIX, and archives. Manually classify fixture false positives. Any real credential leak, unexpected PAYG fallback, hidden provider switch, secret persistence, proof-label confusion, or model authority escalation is a release blocker.

Provider policy blocks and unavailable optional local engines remain truthful non-blocking states. They are never promoted to `VERIFIED`.

## Release Decision

The release matrix records `PASS` only for current real evidence on the named platform. The release is eligible only when both Windows 11 x64 and macOS arm64 complete every mandatory matrix item, the live Codex and C-001 chains pass, all tests and security gates pass, release-check reports ready, the working tree is clean, and `HEAD == origin/main`.

Only then may the agent create the annotated `v1.0.0-rc.1` tag, push it, generate final revision-matched artifacts and SHA-256 checksums, and create the GitHub prerelease. An existing conflicting tag is a blocker and is never overwritten.

If any mandatory gate is unavailable or fails, the final report is `PASS_WITH_GAPS` or `BLOCKED`, with `TAG: NOT_CREATED` and `GITHUB_RELEASE: NOT_CREATED`.

## Final Deliverable

The final deliverable follows the supplied report format and contains only evidence actually produced during this qualification run: start and final revisions, repository state, live-model results, C-001 trust-chain results, separate Windows and macOS matrices, provider results, test totals, security findings, artifact paths and hashes, release actions, exact blockers, and a precise verdict.
